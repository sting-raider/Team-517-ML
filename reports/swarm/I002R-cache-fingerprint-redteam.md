## Results

### Finding 1 — BLOCKING: the existing Modal training path cannot satisfy I002's new manifest requirement

`ber.tune` now requires both:
- `artifacts/address_baseline/features.manifest.json`
- `artifacts/wide_calibration/features.manifest.json`

It calls `read_manifest()` before loading the feature arrays and raises `StaleArtifactError` if either manifest is absent.

However, both pieces of the existing remote-training data path still omit those files:

1. `tools/stage_modal.py --training` uploads only `features.npz` and `anchors.json` for each training artifact directory.
2. `modal_app.train_catboost()` copies only those same four files from the Volume into the fresh scratch directory before calling `python -m ber.tune`.

Therefore a clean I002 Modal training invocation deterministically reaches `ber.tune` without either required manifest and fails before model fitting.

This is more than missing coverage: the exact environment proposed as the remaining I002 validation gate is incompatible with the patch.

**Required fix:** stage and copy both `features.manifest.json` files everywhere the portable training bundle is moved, and add a smoke test that builds a clean training scratch directory from the documented allowlist.

### Finding 2 — HIGH: signed retrieval indexes can be bypassed by existing train-side candidate callers

I002 correctly makes `build_index(c, split)` compute and validate a compatibility fingerprint over the blocker contract and exact rowid-backed inventory.

But `candidates()` itself does not validate the index signature. Two important callers invoke `candidates()` without first invoking `build_index()`:

- `src/ber/retrieval_study.py`
- `src/ber/confirm.py`

Both can therefore consume pre-existing `train_freq` / `train_index` tables whose signature belongs to an older blocker implementation or older prepared inventory.

The retrieval-study path is especially dangerous because it writes `wide_candidates`. `wide_evaluate.py` can then compute a brand-new `features.manifest.json` from the *contents* of that stale candidate relation. The fresh feature manifest proves what rows were materialized, but not that those rows were generated by the current signed blocker/index contract. In other words, stale candidate semantics can be re-signed as a current feature cache.

**Required fix:** make all public candidate-generation entrypoints establish/verify index compatibility before querying the index. The cheap implementation is to call `build_index()` once in `retrieval_study` and `confirm` before `candidates()`; a stronger design also records blocker/index/cap provenance alongside persisted candidate relations so downstream materialization cannot bless an old candidate table.

### Finding 3 — HIGH: deployment candidate-budget calibration still accepts mismatched feature/probability artifacts

`src/ber/candidate_budget.py` directly loads:
- `artifacts/wide_calibration/features.npz`
- `artifacts/tuned/depth10_wide_probabilities.npy`
- `artifacts/wide_calibration/anchors.json`

The only cross-artifact compatibility assertion is:

`len(prob) == len(groups)`

That does not detect same-length row reordering, replacement, or a probability vector produced from a different version of the wide feature cache.

The report produced by this script is not merely diagnostic: `modal_app.score_test()` reads `reports/candidate_budget.json` for non-640 deployments and overwrites the model threshold/candidate cap from it.

Thus a stale-but-same-length feature/probability pairing can still silently determine deployment threshold selection after I002.

`cap_study.py` has the same general direct-cache pattern for baseline features/probabilities and can mutate `model_config.json`.

**Required fix:** make candidate-budget/cap-selection consumers verify:
- the current feature-cache manifest;
- the tuned-trial manifest or an explicit probability-output manifest;
- row/order identity between the probability vector and the feature rows;
- report/config provenance before deployment consumes a threshold.

A small probability sidecar keyed by the exact feature-manifest fingerprint plus row-order/content fingerprint would close this cleanly.

## Positive findings

The red-team does **not** invalidate I002's core provenance primitives.

Static inspection supports these improvements:

- prepared train/test reuse is now tied to all three source-file signatures plus the normalization/load contract;
- unsigned or mismatched prepared split tables fail closed unless explicitly refreshed;
- retrieval-index compatibility binds blocker implementation/config and rowid-backed inventory;
- pair-feature cache identity binds feature code, train/truth/anchor/candidate relations;
- prediction resume identity binds model/config, current verified test index, blocker/features/shortlist/prediction code, and partition parameters;
- manifests self-check their stored identity checksum;
- unsafe relation identifiers are rejected.

The sampled large-file signature remains intentionally non-adversarial. PR #59 already documents that limitation, so it is not treated as a new defect here.

## Error analysis / why existing tests missed these gaps

The 8 provenance tests are helper-level and use fake or filesystem-only fixtures. They do not exercise the repository's orchestration boundaries.

The missed failure classes are all integration/call-graph failures:

1. **Required sidecar omitted during artifact transport.**
2. **Guarded builder exists, but callers can bypass it.**
3. **Downstream consumer combines separately valid files without proving they belong to the same row universe/order.**

These are exactly the failures most likely to survive good unit tests while invalidating experiment comparisons.

## Risks

- Static audit only: no DuckDB or Modal execution was possible in this chat runtime.
- Finding 1 is deterministic from the file allowlists and `ber.tune` precondition.
- Findings 2 and 3 are conditional on stale artifacts being present, but that is the explicit threat model I002 is intended to prevent.
- No challenge metric is changed or re-measured.
- No raw data, predictions, row-level diagnostics, or external identity evidence are committed.

## Recommendation

**REQUEST CHANGES / FOLLOW-UP.**

Do not merge PR #59 as the swarm-wide provenance guard yet. Its core design is worth preserving, but the three paths above leave one deterministic broken production workflow and two material stale-artifact bypasses.

Promotion gate:
1. include manifests in the complete Modal training transport path;
2. verify train retrieval-index compatibility before every persisted candidate-generation workflow;
3. bind candidate-budget/probability consumers to exact feature/trial provenance and row order;
4. run the already-planned real DuckDB smoke plus a clean-scratch Modal training smoke.

## Follow-up tests

After fixes, add focused tests for:

- a clean Modal training bundle contains both feature manifests;
- mutating blocker/index identity makes retrieval study/confirmation rebuild or fail before candidates are produced;
- replacing/reordering a same-length wide feature cache causes candidate-budget selection to fail closed;
- a probability artifact generated for feature-cache A cannot be consumed with feature-cache B even when row counts match.
