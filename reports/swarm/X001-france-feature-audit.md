# X001 — Current feature and retrieval audit for unseen-France robustness\n\n## Hypothesis\n\nThe selected blocker/matcher is nominally language-agnostic, but its preprocessing and context features may encode assumptions learned only from US/India. A static audit plus a full source-one census should identify concrete France transfer risks without inventing French labels.\n\n## Change\n\nNo scoring logic changed. I audited data.py, blocking.py, features.py, fast_features.cpp, shortlist.py, predict.py, and tune.py, covering every selected CatBoost input and the candidate path. I added src/ber/france_audit.py, an aggregate-only census helper; it emits no challenge rows.\n\n## Protocol\n\n- Full train_source1.tsv: 210,069,713 bytes, 2,206,821 rows.\n- Full test_source1.tsv: 175,022,086 bytes, 1,732,544 rows.\n- No sampling. France has 259,452 test S1 rows and no labels.\n- NFKD combining-mark removal is only an accent-sensitivity diagnostic proxy. Production normalization remains DuckDB strip_accents() in data.py.\n- Synthetic CLI sanity check passed on accented French text and verified that row IDs/text are not emitted.\n- The connected runtime cannot materialize the >256 MiB S2/S3 TSVs, so no French pair recall, precision, calibration, or matching score is claimed.\n\nReproduction command:\n\n    python -m ber.france_audit --train-source1 dataset/train/train_source1.tsv --test-source1 dataset/test/test_source1.tsv --out reports/swarm/X001-france-source1-audit.json\n\n## Baseline context\n\nThe selected independent confirmation score is macro F0.5 0.928835, with US 0.948339 and India 0.900722. Candidate pair recall is 0.947246 and blocking-oracle macro F0.5 is 0.980951.\n\nExisting country-transfer stress already shows that nominally language-agnostic features are not country-invariant: US-only training evaluated on India scored 0.777201 versus 0.886178 for mixed US+India training; India-only training evaluated on US scored 0.907797 versus 0.945167 for mixed training. These are not France estimates.\n\n## Results\n\n### 1. Production has no raw/diacritic-preserving matcher view\n\ndata.py stores raw text, but the blocker and all 44 name/address comparison inputs consume only n/a columns produced by lowercasing, strip_accents(), punctuation-to-space normalization, and trimming. The native fast-feature path receives the same normalized strings. Country-local retrieval creates a hidden distribution shift\n\nThe blocker hashes (country, key), which is reasonable because the supplied training audit found zero cross-country positive links. However, retrieval is a sum of fixed bonuses plus ln(10000001/freq), and key_hits counts surviving keys. freq is computed inside the country-specific index and postings above 1,000 are discarded. Therefore a French pair with the same lexical relationship as a US pair can receive a different retrieval score/key count solely because French corpus frequencies differ. Those values are direct CatBoost predictors, not just retrieval metadata.\n\nThis is the strongest feature-level calibration risk found in X001 because it follows mechanically from the implementation and does not require French labels.\n\n### 4. Address blocking is only partly language-neutral\n\naddress_words() removes an English-oriented stoplist: road, street, avenue, drive, lane, floor, near, opposite, the, and, unit, plot, no. High-frequency French tokens will often be removed anyway by the posting-frequency cutoff, so the stoplist is not automatically harmful. Still, it is asymmetric across languages.\n\nFrench S1 frequent address tokens include rue (170,819 rows), avenue (30,987), allee (12,038), bis (11,010), and boulevard (9,310). Frequency-based suppression is safer than adding an ad-hoc French stopword list.\n\n### 5. One mixed model and one global threshold remain unvalidated for France\n\nCountry is not passed into CatBoost, which avoids a closed US/India category failure. But the model and threshold are learned only from US/India, and the existing US↔India transfer degradation demonstrates that the current feature distribution is not invariant. France calibration remains unknown.\n\n## Interpretation\n\nThe highest-confidence issue is not that accent folding is bad. Folding often improves recall. The issue is that folding is the only text view, despite France containing much more diacritic and punctuation structure than the labeled data.\n\nThe next-highest risk is the learned use of raw country-relative retrieval scores. Even perfectly language-neutral string similarities can drift if their retrieval priors change with country-local corpus frequency.\n\nUnweighted token overlap is a precision risk because common French legal-form and address tokens contribute the same overlap counts as distinctive terms. Number-conflict and missingness features are the safest current cross-country signals and should be preserved.\n\n## Risks\n\n- No France labels exist; no French F0.5 is claimed.\n- S2/S3 could not be materialized in this chat because each exceeds the connector's 256 MiB limit.\n- NFKD is a diagnostic proxy, not a claimed clone of DuckDB strip_accents().\n- S1 token frequencies do not replace the S2/S3 posting frequencies used by the blocker.\n- US↔India transfer results are stress evidence, not France estimates.\n\n## Recommendation\n\n**FOLLOW-UP.**\n\n1. Require same-slice or transfer gains before promotion.\n2. Keep same-country blocking for now because all supplied positive labels agree on country, but separately test a tiny country-agnostic rescue channel before treating country as an absolute veto.\n\nNo production scoring change should be merged from X001 alone. The audit identifies measurable mechanisms; it does not manufacture a French validation score.
