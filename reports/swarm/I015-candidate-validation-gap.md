# I015 — Fail-closed candidate validation audit

## Hypothesis

The final completion path might be able to record `PASS` without validating
`candidate_pairs.tsv`, creating a final-archive integrity risk even when
`matching_results.tsv` is valid.

## Change

The hypothesis was red-teamed against current main
`2a2ae6ec6de943ad7e38ecc0f0a95b53a0d7f460` and the supplied challenge
`utils/validate_submission.py` from the shared Drive.

Two small provenance/documentation changes were made:

- `tools/finish_submission.py` now records the scope of the two validation
  layers explicitly in `completion.json`.
- `MODAL.md` no longer recommends feeding the complete full-data candidate
  file to the organizer validator by default; it documents the bounded-memory
  Team 517 validation layer and keeps the organizer candidate check optional
  when sufficient RAM is available.

No retrieval, matcher, threshold, candidate-budget, or output-generation logic
changed.

## Baseline

The selected full test export documented on main contains:

- 1,732,544 Source-1 rows
- 256,724,515 candidate pairs
- 5,881,092 predicted matches

The selected Modal run uses candidate cap 160. The current calibration report

## Results

### 1. The initial failure hypothesis is rejected

`tools/finish_submission.py` does **not** send `candidate_pairs.tsv` to the
organizer validator, but immediately before that it calls Team 517's
`ber.validate` on both files.

That streaming validator enforces the candidate contract needed for the final
artifact:

- exact candidate header
- exactly one row per sorted test Source-1 entity
- no duplicate candidate IDs inside an anchor
- legal S2/S3 target prefixes
- no extra rows
- every predicted match is a subset of the exported candidate set

Therefore the completion path cannot normally record `PASS` with a missing,
malformed, row-misaligned, duplicated, or prediction-inconsistent candidate
file.

### 2. The exported candidate boundary is correct

In `ber.predict.score_batch`, `shortlist_rows` is applied before feature
construction and CatBoost scoring. The `considered` mapping is populated only
from those shortlisted/scored records and is written directly as
`candidate_pairs.tsv`.

So the file is the final matcher input boundary, not an earlier wider retrieval
union.

### 3. Forcing the organizer validator over the full candidate file is a bad default

The supplied organizer validator constructs an in-memory
`{source1_id: set(candidate_ids)}` mapping. Its own documentation warns that
ID checking costs a few GB and more when the candidate file is included.

The repository already documents a complete test export with 256,724,515
candidate pairs. Making the organizer `--candidate` path mandatory in
`finish_submission.py` would duplicate checks already performed by
`ber.validate` while creating a substantial avoidable OOM risk on ordinary
laptops.

This is why the implementation was **not** changed to force
`--candidate`.

### 4. One diagnostic remains intentionally optional

The routine final path calls `ber.validate(..., check_ids=False)`, so it does
not rescan the complete candidate file to prove that every target ID exists in
the test S2/S3 inventory.

This is lower risk than the formatting/subset checks because production
candidates are generated by joining target row IDs back to the supplied
`test` table before export. Shard checksums and final output SHA-256 values
also guard accidental output mutation. A full target-ID existence scan remains
a useful one-off release diagnostic when resources permit, but it should not be
confused with a required scorer gate.

### 5. Documentation/provenance inconsistency fixed

`README.md` already warns that the supplied validator can exceed laptop RAM
when the complete candidate file is included. `MODAL.md` nevertheless told
users to run that exact full-candidate command after download.

The branch now makes the safe layering explicit:

1. Modal merge / `finish_submission.py`: bounded-memory `ber.validate` over
   matching + candidate files.
2. Post-download organizer validator: matching file by default.
3. Organizer `--candidate` and `--check-ids`: optional deeper checks when the
   machine has sufficient RAM.

`completion.json` now records both validation scopes so a future operator does
not mistake an organizer matching-only exit code for the entire validation
story.

## Error analysis

Potential final-artifact failures were checked separately:

- **Wrong candidate header/row count/order:** caught by `ber.validate`.
- **Duplicate or malformed candidate IDs:** caught by `ber.validate`.
- **Prediction outside candidate set:** hard failure in `ber.validate`; only a
  warning in the supplied validator, so Team 517 is stricter here.
- **Candidate file not representing matcher input:** not present; export occurs
  after shortlist selection and before/alongside scoring.
- **Unknown but syntactically valid S2/S3 ID:** not checked in the default full
  path; optional deep diagnostic only.
- **Validator OOM:** plausible if the supplied validator is given the complete
  256M-pair candidate file; documentation now avoids making that the default.

## Interpretation

The original suspected submission bug was mostly a false positive caused by
looking only at the organizer-validator command. The pipeline uses two
validation layers, and the internal layer already covers the candidate file in
the memory-safe path.

The useful fix is therefore provenance and operator guidance, not replacing a
bounded-memory check with a more memory-hungry duplicate.

## Risks

- No executable regression test ran in this chat because the shared
  Python/container backend returned `ClientError`.
- The full target-ID existence scan has not been timed on the 256M-pair export,
  so it is not promoted into the mandatory release path.
- The organizer may change final packaging/validation rules; the supplied
  challenge validator remains the source of truth for the current artifact
  contract.

## Recommendation

**REJECT the hypothesis that the final path fails to validate
`candidate_pairs.tsv`. PROMOTE the documentation/provenance clarification.**

Do not force the organizer `--candidate` mode on the full 256M-pair export by
default. Keep the bounded-memory `ber.validate` check mandatory and run deeper
ID-existence validation only as a resource-aware release diagnostic.
